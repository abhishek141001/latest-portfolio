Start here

You do not need magic prompts.

This guide comes from real work: 208 sessions with coding AI, 1,866 human messages, 667 code changes, and 200 pull requests at a live Indian startup doing about $10M in yearly revenue with 100,000+ paying customers.

What the record showedWhat it means
67 characters median prompt lengthMost useful steering was short; the agent already had durable context.
21% of prompts carried screenshotsThe screenshot, portal response, log, or number was often the real bug report.

The thesis: the leverage was not longer prompts. It was feeding the agent reality—the business rule, precedent, raw evidence, expected number—and checking the result against reality.

01 / Start right

First, make sure you are in the right project and branch.

A branch is a separate version of code. A worktree is a separate folder for that version. If you look at an old branch, you can give AI a perfect task and still get the wrong answer.

First action, every time

  1. Fetch the remote base
    Do not treat a local branch called prod as production.
  2. Name the worktree
    One task, one worktree. Parallel agents do not share uncommitted edits.
  3. Read production explicitly
    Inspect the remote base when behavior must match a live path.
  4. Locate the real environment
    Confirm repository, service, worker, and data source before diagnosis.
  5. Record the base
    Put branch and commit in the task brief or memory entry.
  6. Only then investigate
    Now the agent has a trustworthy reality to inspect.
Hard-won rule: never commit from a worktree while an agent is editing it. A broad git add -A can sweep up its partial work; wait for the owner or let that agent commit its slice.

03 / Give AI the right background

Do not throw files at AI. Tell it the few things that matter.

More tokens do not automatically mean better work. Give the agent the smallest set of facts needed for its next correct decision: goal, gate, existing precedent, system constraints, relevant code, raw evidence, and behavior checks.

Not helpfulHelpful
“Make sign-up better. Look around.”“Follow the current sign-up path. Do not change anything yet. Tell me which pages, files, and checks are used.”
“Use how we already build things.”“Put the checking rule in the same place as the existing sign-up checks. Do not overwrite a support person’s choice.”
“Handle missing details.”“If a needed detail is missing, ask for help. If it is clearly wrong, show a clear message. A support person’s choice always wins.”
IntentWhat outcome changes?
Ground truthWhich rules and files are authoritative?
VerificationWhat behavior proves it works?
Name the precedent: “Match X” is usually stronger than a page of invented architecture. It prevents a second validator, date helper, API client, or flow from appearing beside one that already works.

04 / Look first

Ask AI to look around before it changes code.

The first request should reduce uncertainty, not create a diff. When the problem is not yet understood, use diagnosis-only mode: ask what is wrong, ask for evidence, and explicitly forbid edits.

You are investigating a feature. Do not modify files. 1. Trace a sign-up request from the form to its final result. 2. List the files that own the checks, status changes, notes, and customer message. 3. Find tests that cover each path. 4. Identify risks, especially sending two messages or overwriting a support person’s choice. 5. Propose a minimal plan. For each step, name the file and test. Return: findings, unknowns, plan, and what you deliberately will not change.

Give bugs as falsifiable evidence

  • Attach the artefact: screenshot, raw portal error, log line, or response body.
  • Name what happened and the exact value or behavior that should have happened.
  • Withhold your diagnosis until the agent has inspected the evidence.
  • On the second report, add a working sibling, a narrower value, or a new log—not the same complaint.

05 / Work in small steps

Do not ask AI to do everything in one go.

Long autonomous runs are useful only when each checkpoint has a small, observable output. A good workflow preserves your ability to redirect before the wrong assumption reaches five files.

  1. Investigate
    No edits. Ask for paths, behavior, tests, risks.
  2. Plan
    Review file-by-file plan and cut scope.
  3. Implement
    One bounded slice; require tests.
  4. Self-review
    Ask agent to criticize its own diff against criteria.
  5. Adversarial review
    Fresh context: find what could break.
  6. Run + inspect
    Tests, diff, logs, actual user journey.
Rule of thumb: you should be able to explain every changed file in one sentence. If you cannot, the batch was too large.

The exact command syntax differs between tools. The operating model does not: plan first, keep scope explicit, demand evidence, and review every consequential change.

09 / Ask someone to find mistakes

Ask a fresh AI chat to try to break the change.

The AI that wrote the code may miss its own mistake. Open a fresh AI chat and ask it to look for problems. This is extra helpful for login rules, repeated actions, lost data, and anything a user cannot easily undo.

Review this diff as a production engineer. Do not rewrite it. The feature must: preserve manual overrides, emit audit entries, avoid duplicate messages, and send missing details to the support team. Check for: - behavior that violates an acceptance criterion - missing or misleading tests - unauthorized state transitions - race conditions / retries / duplicate events - sensitive data in logs - backwards compatibility risk For every finding, cite file + line, severity, failure scenario, and the smallest credible remediation. If no finding, state what you could not verify.

Do not accept this review output

“Looks good,” “consider adding error handling,” or a long list without file evidence. The agent must connect each concern to a real execution path.

10 / Fix bugs with clues

Use facts first. Do not let AI guess a fix.

AI is good at making believable guesses. Do not let a believable guess become a fix. First collect clues: what the user saw, the error message, and what number or result should have appeared.

SYMPTOM
→
OBSERVE
→

→
TEST

Example: sign-up messages are stuck

Weak request“Why are messages stuck? Fix it.”
Strong request“Look at the logs and code for three customer requests. Make a timeline. Do not change code until you find what they all have in common.”
Rule: a fix is not complete until the original symptom can no longer recur under a test, monitor, or invariant.

12 / Remember what you learn

Write down what surprised you so nobody has to learn it twice.

Production changes teach you which assumptions were false. Capture that learning while the details are fresh, then turn it into a rule, fixture, test, runbook entry, or context file. In the field record, 133 durable memory files made this work survive context windows and agent changes.

What surprised us?Which workflow detail was missing from the ticket?
What did the agent assume?Which assumption was plausible but wrong?
What signal was missing?Which log, metric, or audit detail would have shortened debugging?
What becomes reusable?Which test fixture or brief template should be kept?
Memory rule: record only what was observed. Label inference, assumption, and untested claims as unverified. Keep the hypothesis you killed, the baseline failure count, the blast radius, and the external verdict verbatim.

If you type an instruction twice, move it into the right durable layer: workspace instructions for standing defaults, a skill for domain maps, an agent definition for role behavior, or memory for observed facts.

The useful mindset

Care about the person using it, not only the code task.

A useful AI-native engineer is not someone who produces the most code per hour. They reduce the time from unclear problem to trusted outcome.

Ticket mindsetFDE mindset
“What should I build?”“What decision or workflow should improve?”
“The requirements were incomplete.”“Here are the unknowns and the lowest-risk way to resolve them.”
“The tests pass.”“The behavior is observable, safe to release, and works for the user.”
“The agent implemented it.”“I can explain why this design is correct and what it cannot guarantee.”
AI makes implementation cheaper. It makes judgment, discovery, verification, and ownership more visible.
The honest caveat: speed can hide weak review. The record contained zero explicit test requests in sampled sessions, many symptom-only re-reports, and long sessions that needed repeated compaction. Keep the fast empirical loop—but add a diff glance, targeted test, fresh review pass, and a work-in-progress limit.

A simple weekly habit

How to use this on your next small feature.

  1. 30 minutes: discovery
    Write the decision brief. Speak to the workflow owner if one fact is uncertain.
  2. 30 minutes: repository trace
    Let an agent investigate without edits. Verify its file map.
  3. 20 minutes: scope
    Write acceptance criteria, invariants, and out-of-scope items.
  4. 45 minutes: implementation
    Delegate one bounded slice. Keep every diff explainable.
  5. 30 minutes: adversarial review
    Use a fresh context to attack assumptions, tests, and failure modes.
  6. 30 minutes: release design
    Choose a rollout, signals, stop condition, and recovery path.
Do not optimize this schedule. It is a forcing function that keeps the highest-leverage thinking before the lowest-leverage typing. Adjust duration, not order.

One-page checklist

Use this before you say “done.”

Establish + map

  • Fresh remote base and correct worktree confirmed
  • Named user, business gate, and decision
  • Current workflow and precedent documented
  • Human owner and override path clear
  • States and external boundaries mapped

Brief + delegate

  • Raw evidence and expected value attached
  • Acceptance criteria observable
  • Out-of-scope work explicit
  • Scout investigated before builder edits
  • Tasks are independently reviewable

Verify

  • Happy, edge, failure, and retry cases tested
  • Manual decisions are preserved
  • Fresh adversarial review completed
  • Screen, network, logs, database, and diff inspected
  • Baseline failures separated from new ones

Ship + learn

  • Dry run → 2 → 10 rollout exists
  • Signals, stop condition, and recovery owner named
  • Blast radius stated, including what does not change
  • Customer data absent from pushed artifacts
  • Observed learning written to durable context
The standard: not “the agent finished.” Not “the build passed.” A real outcome is understandable, testable, observable, and recoverable.

Finish

Use AI to build faster. Keep thinking for yourself.

The durable advantage is not knowing a magic prompt or a particular tool. It is knowing how to discover a real problem, give implementation the right constraints, verify the result, and take responsibility for what reaches users.

Claude Code and Codex can make a capable engineer dramatically faster. They cannot make an unclear workflow clear, decide whether a business rule is right, notice an unspoken exception, or accept the consequences of a bad release.

That remains the work. It is also the opportunity.
